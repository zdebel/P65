# sdk/ - extract of the Raspberry Pi Pico SDK

This directory is **not** the whole Pico SDK. It is an extract of

* **Raspberry Pi Pico SDK 1.5.1** - <https://github.com/raspberrypi/pico-sdk>, tag `1.5.1`
  (commit `6a7db34ff63345a7badec79ebea3aaef1712f374`), and
* **TinyUSB 0.15.0** - <https://github.com/hathach/tinyusb>
  (commit `86c416d4c0fb38432460b3e11b08b9de76941bf5`), the USB stack the SDK bundles in `lib/tinyusb`,

containing only the files the P65 firmware needs to build: **219 files, 4.6 MB**, so that the
firmware can be built with a plain `Makefile` and without installing the SDK or CMake.

The selection is for exactly this configuration: RP2040, board `pico`, 2 MB flash, USB serial
(`stdio_usb`), multicore, flash programming (`pico_flash`), I2C, SPI, PIO, DMA, hardware
floating point routines from the boot ROM (`pico_float` / `pico_double`).

## What is in it

The directory layout is the SDK's own (`src/...`, `lib/tinyusb/...`), so every file can be
compared with, or replaced by, the original at the same relative path.

| | |
|---|---|
| `src/common/`, `src/rp2_common/`, `src/rp2040/`, `src/boards/` | the SDK libraries used (`hardware_*`, `pico_*`), their headers and the chip's register headers |
| `src/rp2_common/pico_standard_link/memmap_default.ld` | linker script |
| `src/rp2_common/boot_stage2/` | second stage boot loader source (`compile_time_choice.S` -> W25Q080 variant), its linker script and `pad_checksum` |
| `lib/tinyusb/src/` | TinyUSB device stack (CDC is the only class used; the other classes compile to nothing with the SDK's configuration) |
| `sdk.mk` | **not from the SDK:** list of the files that get compiled and the linker's `--wrap` list, taken from the SDK's CMake build of this firmware; included by `../Makefile` |
| `generated/pico_base/pico/` | `version.h` (as generated by the SDK's CMake) and `config_autogen.h` (written by hand: the SDK generates it with absolute paths; it only includes the board and CMSIS headers) |
| `LICENSE.TXT`, `lib/tinyusb/LICENSE` | licenses |

All other files are **unmodified copies** (byte for byte) of the originals. Nothing from the SDK's
`tools/` (pioasm, elf2uf2, picotool), CMake files, examples, documentation, other boards, the RP2350
or other TinyUSB ports and classes is included.

## Build equivalence

`make` produces `out/p65.bin` and `out/p65.uf2` **bit-identical** to the build with the SDK's CMake
(checked on 2026-11-20 with xPack Arm GNU toolchain 15.2.1 on the firmware of that day).

## Licenses

The Pico SDK is BSD-3-Clause (`LICENSE.TXT`), TinyUSB is MIT (`lib/tinyusb/LICENSE`); the SDK
also contains a few files from other authors under their own (permissive) licenses, always stated
in the header of the file (for example `pico_printf`, derived from Marco Paland's printf, MIT).
Keep these headers and the license files when copying anything from here.

## Updating or adding SDK parts

The extract was made from a normal SDK build, so a new SDK is taken the same way:

1. Get the new SDK (with its `lib/tinyusb` submodule) somewhere outside this repo and build the
   firmware once with the SDK's own CMake, with a minimal `CMakeLists.txt` such as

   ```cmake
   cmake_minimum_required(VERSION 3.12)
   include($ENV{PICO_SDK_PATH}/pico_sdk_init.cmake)
   project(p65 C CXX ASM)
   pico_sdk_init()
   add_executable(p65 <the sources listed in ../Makefile (FW_SRCS)>)
   pico_generate_pio_header(p65 ${CMAKE_CURRENT_LIST_DIR}/src/65c02_clk.pio)
   target_include_directories(p65 PRIVATE include)
   target_link_libraries(p65 pico_stdlib pico_multicore pico_flash hardware_dma hardware_exception
                         hardware_flash hardware_gpio hardware_i2c hardware_pio hardware_spi)
   pico_enable_stdio_usb(p65 1)
   pico_enable_stdio_uart(p65 0)
   pico_add_extra_outputs(p65)
   ```
2. Find the files really used: `ninja -t commands p65` in the build directory lists every
   compiled file and the link command, and `gcc -M` with the same flags lists the headers.
3. Copy them into this directory under the same relative path, update `sdk.mk` (source list, link
   order, `--wrap` list) and the version numbers above, and check that `make` produces the same
   image as that CMake build (`out/p65.bin`).

If the firmware starts using another SDK library (say `hardware_pwm`), its files have to be
added the same way - the build fails with a missing header or an undefined reference otherwise.
